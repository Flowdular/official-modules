# Contributing to official modules

Changes here become editable source releases installed into other people's Flowdular workspaces. Keep the specification, implementation, tests and release evidence in agreement.

## Choose the owning repository

Business behavior for expenses, parties and catalog belongs here. Runtime, authentication, CLI, shared UI and sandbox changes belong in [Flowdular core](https://github.com/Flowdular/flowdular). Website changes belong in [landing](https://github.com/Flowdular/landing).

For a new module or a breaking behavior change, open an issue describing the user need, scope, public contracts and compatibility impact before implementation. New modules require an explicitly approved `spec/module.yaml`. An agent must not approve its own specification or carry approval forward after the specification changes.

## Set up

Use Node.js 24 and the pnpm version pinned by this repository:

```sh
pnpm install
pnpm verify
```

The initial Flowdular SDK publication is pending. Until the declared npm versions exist, maintainers use the tarballs generated by `pnpm release:pack` in the core repository. Keep local tarball overrides and machine-specific lock files out of commits. Do not replace pinned dependencies with arbitrary versions to get an installation to pass.

## Make a change

1. Read the module specification, manifest, owning implementation and tests.
2. Define the expected behavior and failure cases. For a bug, add a regression test that fails before the fix.
3. Implement through public Flowdular contracts. Keep module ID, package name, manifest version and specification version aligned. Changes to released source require a new version.
4. Run the affected checks, then `pnpm verify` for the repository.
5. Review the final diff separately from implementation. Fix findings and repeat the affected checks before recording evidence.

Preserve these contracts:

- Resolve tenant identity from the authenticated principal. Use explicit permissions, bounded input and CSRF protection for mutations.
- Use bound SQL and tenant-scoped transactions. Tenant tables enforce row-level security. Never read another module's database; use a declared public capability.
- Leave applied migrations unchanged. Add the next migration and keep embedded migration SQL identical to the file.
- Declare module and package dependencies. Test against their stated compatible versions.
- Use the shared UI and translation runtime. Keep English and Polish translations aligned, and verify loading, empty, error, populated and denied states when changing a screen.
- Preserve idempotency, cleanup and recovery for background work. Do not put credentials in source, logs or review evidence.

## Test behavior

`pnpm verify` runs typechecking, tests and module validation. CI also runs tests against PostgreSQL with restricted roles. Tests must demonstrate the changed behavior at its public boundary, including relevant denial, tenant isolation, validation and failure cases.

Cross-module integration tests live in `tests/consumer/`. Keep them here when they exercise business modules together with the core harness. Do not replace them with mocks that bypass the contract being tested.

Report skipped or unavailable checks explicitly. A command that was not run is not passing evidence. Do not weaken assertions to make a release pass.

## Review evidence

Each release uses `reviews/<module-id>.json`. It contains:

- `sourceSha256`, calculated from the exact allowlisted source;
- the requirements checked;
- findings, which must be empty before packaging;
- successful `typecheck`, `test` and `validate` checks, with their actual commands and exit codes.

Use `readModuleSource` and `sourceDigest` from `@flowdular/cli/distribution` to calculate the source hash. Follow the existing review files for the schema. Recalculate evidence after any source change; never copy a passing report onto different source.

Automated checks and self-review support maintainer review. They cannot establish that an arbitrary publisher or review report is trustworthy.

## Prepare a release

Only package a reviewed version after its required checks pass:

```sh
pnpm verify
pnpm release:pack --local
```

The packer checks source identity, review evidence, file bounds and paths, and refuses to overwrite different bytes at an existing release version. If it reports an immutable-version conflict, increment the module, package and specification versions and review the new source. Never delete an old artifact to bypass that protection.

Commit the module source, review records and new `registry/releases` artifacts together. Then generate the public catalog:

```sh
pnpm release:pack --index-only
```

Commit `registry/index.json` separately. Its artifact URLs now reference the exact committed source/artifact revision. Keep historical versions available. Run CI before publishing the release commits to `main`.

For a local installation test, use the generated catalog in a disposable Flowdular workspace:

```sh
pnpm flowdular module install expenses.core@0.6.0 \
  --registry /absolute/path/to/official-modules/registry/local-index.json
```

That command previews the plan. Add `--apply` to exercise writing source, then enable the module and run the consumer's validation and tests. Use the version being reviewed. `registry/local-index.json` is a local artifact and must not be published as the official index.

Official business modules are distributed through this source catalog. The separately published npm SDK is owned by the core release process.

## Pull request checklist

- Describe the user-visible change and link its issue or approved specification.
- Explain public API, dependency, permission and migration changes.
- Include actual test commands and results, with any unavailable checks.
- Include updated review evidence for release source.
- Include screenshots for changed screens, with no secrets or real tenant data.
- Confirm no local overrides, generated runtime state or unrelated changes entered the diff.

Keep the PR description focused on the final behavior. Maintainers should be able to reproduce the evidence from the repository.
